# GardenForge audit, October 2026

Status of the code audited: branch `audit/roadmap-and-small-fixes` at the commit that adds this file.
Findings are numbered F01–F84; the full table is in Appendix A. Severity is judged for a one-household
app whose primary device is an iPhone: **high** means data loss or a blocked owner goal, **medium** a real
defect with limited reach, **low** polish.

## Scope and method

Nine review passes, one per dimension (data loss and persistence, service worker and deployment, iPhone
and mobile UX, photo journal, accessibility, logic and validation, architecture, horticultural data
integrity, security and privacy), each run against the real `index.html` served locally and driven with
Playwright in Chromium at 320 px and 390 px. 98 raw findings were merged into 84. Of those, 66 were
confirmed by running the app, 12 by reading the code, and 6 rest on external documentation. 14 findings
(every high one plus the medium ones with weaker evidence) then went through an independent refutation
pass; its verdicts are in Appendix A.

Two limits apply to everything below:

- Chromium is not Safari. Anything marked *needs device verification* was reasoned from WebKit
  documentation or community reports and must be checked on a real iPhone.
- The sandbox could not reach `agrilife.org`, `tamu.edu`, `webkit.org`, `vercel.com` or
  `web.archive.org`. No planting window or maturity value could be compared with the cited guide, and
  no Vercel or Safari behaviour could be read from primary documentation. Those items are flagged as
  owner-review tasks rather than guessed at.

## Summary

The foundation is better than most single-file apps: user text is escaped consistently, the service
worker never caches personal data, destructive actions confirm, dates and soil arithmetic are correct
(including planting windows that cross New Year), and the horticultural copy is honest about what is
sourced and what is an estimate. The serious problems are concentrated in three places:

1. **Durability of the owner's records.** Photos are in no backup or export path, and the backup UI
   implies they are (F01). Until this branch, a saved garden that failed validation at boot was replaced
   by an empty one and overwritten on the next save, and the 1500-record cap made that reachable through
   normal use (F02, fixed here). Failed saves are invisible on a phone (F09). Nothing requests persistent
   storage or reminds the owner to back up (F36).
2. **The photo journal is a prototype.** It refreshed itself in a loop (fixed here), shows at most six
   photos with no timeline or full-size view (F08), stamps save time instead of capture time (F10),
   cannot edit a photo's notes (F24), decodes full-size images for thumbnails (F35), leaves orphans when a
   planting is deleted (F06), and hangs silently when storage is full (F17). The owner's goals
   (individual plants, growth charts, Day 1/30/60 comparisons, harvest and pest records) need the data
   model in `docs/DATA-MODEL.md`, not patches to this store.
3. **No safety net.** There were no tests, no CI, and three hand-maintained version strings. A naive
   move of the script into `app.js` would silently break the portable HTML export (F03). Toasts raised
   while a dialog is open are hidden behind it, so several validation errors and the new photo-save error
   are never seen (F04).

## Findings by theme

### Data durability (F01, F02, F06, F09, F11, F12, F13, F25, F36, F61, F62)

- **F01 (high).** `exportJSON`, the portable HTML copy and the copy/paste backup serialise `state`
  only. IndexedDB photos are never exported and `importFile` never touches them. The dialog copy ("Save
  app with my garden included") says otherwise. A new phone, cleared site data, or app deletion loses
  every photo. This is the first roadmap item.
- **F02 (high, fixed).** Boot validation failure used to start the app empty and the next save wrote
  the empty garden over the real one; `exportJSON` calls `save()` first, so following the warning's advice
  destroyed the data. Measured end to end with 1501 journal entries.
- **F06 (medium).** Deleting a planting or importing a backup leaves its photos as unreachable orphans
  (measured: 3 photos, 84 KB, left behind). The confirm text does not mention photos. There is no photo
  library view.
- **F09 (medium).** `save()` swallows the exception; both status indicators are `display:none` at phone
  widths; callers toast success anyway. Measured at the Chromium quota (5.2 MB): the note was gone after
  reload with no warning. Partly mitigated here (first failure now toasts), but the toast is transient and,
  per F04, invisible when a dialog is open.
- **F11, F12, F13 (medium, partly fixed).** Backups that pass validation but crash a page: `completed:
  null` and missing `draft.rates` are now rejected and boot has a recovery path; a planting with a missing
  `harvestMax` still throws on the Garden page, and a numeric custom-crop name throws on Calendar. Import
  still commits state before rendering it.
- **F25 (medium).** Saved recipes are not held to the draft's unit/target rules; loading one without a
  unit persists a draft the next boot rejects. The recovery slot now protects the data, but the
  downloaded copy cannot be re-imported without hand editing.
- **F36 (medium).** No `navigator.storage.persist()`, no last-backup timestamp, no reminder, and no
  in-app explanation that a Safari tab and the Home Screen app have separate storage. *Needs device
  verification* for the exact WebKit eviction rules.
- **F61, F62 (low).** The import limit (3 MB) is tighter than the pretty-printed export; the portable copy
  "newest wins" rule can replace newer local data because exporting bumps `updatedAt`.

### Photo journal (F08, F10, F17, F24, F26, F35, F39, F56, F57, F71, F72)

- **F17 (medium).** A storage-quota failure during the IndexedDB write fires `abort`, not `error`, so
  `photoPut` never settles and the new try/catch never runs: dialog stuck, submit disabled, no message.
  Measured with a 50 KB quota override. Fix: reject on `tx.onabort` in a shared transaction helper.
- **F10 (medium).** Timestamp is save time; EXIF `DateTimeOriginal` is discarded by the canvas re-encode
  and there is no date field. A library photo from June is dated today. GPS removal is a privacy plus and
  should stay. The v2 photo asset design records `capturedAt` separately from `recordedAt`.
- **F08 (medium), F24 (medium).** Six newest photos only, no full-size view, no edit of
  height/stage/notes; a typo means deleting the photo.
- **F35 (medium).** Each 150 px tile decodes a 1600×1200 JPEG; every save or delete refreshes every
  gallery. Likely to hurt after one season on an iPhone. *Needs device verification* for the memory limit.
- **F26 (medium).** A new connection per call, never closed, no `versionchange` handler. A second tab
  opening version 2 of the database was blocked indefinitely in the test. Any photo-store migration needs
  this fixed first.
- **F39 (medium, fixed on this branch pending device check).** `capture="environment"` likely forces
  the camera on iOS, which contradicts the helper text and blocks choosing an existing photo. The attribute
  is removed on this branch; *needs device verification* that the picker now offers both Camera and Photo
  Library. A valid image with an empty or generic MIME type is still refused by the type check.
- **F57, F72, F56, F71 (low).** Height stored as a string with a per-photo unit, no size/mime/hash, no
  duplicate detection, one bad record blanks a whole gallery, very large originals are fully decoded
  before downscaling.

### Service worker, PWA and deployment (F18, F28, F29, F40, F52, F59, F60, F64)

- **F18 (medium).** The navigation handler stores *any* OK same-origin navigation as the shell. Measured:
  visiting `/manifest.webmanifest` replaced the offline shell with the manifest JSON until the next online
  load. Harmless today; a problem the day `/api/*` exists. Cache only the root/`index.html` HTML.
- **F28 (medium).** Network-first with no timeout: a 12 s server delay meant a 12 s blank app despite a
  cached copy. Race the fetch against a 3–4 s timer.
- **F29 (medium).** Adding `app.js` to `ASSETS` as cache-first while the shell is network-first gives a
  new shell running old code after a deploy. Any file split must add a network-first branch for same-origin
  scripts and styles.
- **F40 (low after verification, dormant).** If the host ever redirects `/index.html` to `/`, `addAll`
  stores a redirected response that Chromium refuses to serve for a navigation. Vercel's default does not
  redirect and `vercel.json` sets no `cleanUrls`, so it is latent; the simplest hardening is to try
  `caches.match('./')` first. Verify the redirect status on the live site.
- **F60, F52, F59 (low).** Updates are only discovered on navigation and the banner is unreachable while a
  dialog is open; the offline badge means "a worker is active", not "the shell is cached"; icon-only
  changes never reach installed phones unless `sw.js` changes.

### iPhone and mobile UX (F04, F14, F15, F53, F65, F66)

- **F04 (high).** `#toast` is a sibling of the modal `<dialog>`, which sits in the top layer, so every
  toast raised with a dialog open is covered: "Enter a valid outdoor date", the maturity check, the bed
  dimensions check, "Choose or take a photo first", and the new photo-save failure. Measured with
  `elementFromPoint` on phone and desktop. Fix: a live region inside the dialog body that `toast()` targets
  while a dialog is open.
- **F14 (medium).** iPhone landscape (852–956 px) falls through the 850 px breakpoint into the desktop
  layout: fixed sidebar that cannot scroll, 14 px inputs (zoom on focus), small targets, and the download
  path instead of the share sheet.
- **F15 (medium).** Changing the mix template, Load, Start blank or "Scale a fill mix" replaces the
  working draft with no confirmation or undo.
- **F53, F65, F66 (low).** A few targets under 44 px, 14 px month selects below 375 px, dialog keyboard
  offset and footer overhang; *needs device verification*.

### Accessibility (F19, F20, F32, F33, F34, F46, F47, F54, F55, F67, F68, F69)

- **F19 (medium).** Every in-page re-render drops focus to `<body>`; ticking a task, changing a filter or
  status, or stepping a month restarts a VoiceOver or keyboard user at the top.
- **F20 (medium).** `--muted` (#637468) is 4.5:1 on the page background and 4.15:1 on sage panels; one
  token change fixes it.
- **F32 (medium).** Ingredient and amendment safety notes ("pre-moisten, check pH", "not a pesticide-rate
  calculator") exist only as `title` tooltips, which iPhone users never see.
- **F33, F34 (medium).** Input borders, focus ring and selected-state fills below 3:1; the owner's own
  photo notes render at 10 px in fixed pixels.
- **F46, F47, F54, F55, F67, F68, F69 (low).** Heading order, dialog-close focus target, colour-only
  Month/Year state, two unlabelled controls, repeated buttons with identical names, chatty live region,
  placeholder contrast in WebKit.

### Logic and validation (F05, F07, F16, F42, F43, F44, F49, F50, F51, F70)

- **F05 (medium).** Custom-crop `harvestMin`, `harvestMax`, `method` and `source` are neither
  type-checked nor escaped in four places, so a crafted backup runs script in the app's origin. Needs the
  owner to import a hostile file, so low likelihood, but it is the one escaping gap found in about 150
  interpolations and it matters more once sync tokens exist.
- **F07 (medium).** `n(x, fallback)` treats an empty field as 0, so a blank "days between plantings" saves
  one-day spacing and a blank lead time saves one week, while the preview shows something else.
- **F16 (medium).** Task check-offs are keyed by task identity, not date; rescheduling a planting hides its
  main reminder, and setting status to Planted does not complete the planting task.
- **F42–F44, F49–F51, F70 (low).** Preview loop on an unclamped repeat count, mix name wiped on edit after
  recipe deletion, `undefined` carried-in fractions treated as known 0 %, a lone CR survives ICS escaping,
  unit-switch rounding drift, a 02-29 window start in non-leap years, a hidden invalid lead-time field
  blocking submit.

### Architecture and maintainability (F03, F21, F22, F29, F30, F31, F45, F73, F74, F75, F76, F77)

- **F03 (high as a gate on refactoring, not a bug in the shipped app).** The portable HTML export works
  only because everything is inline; the same app with `app.js` external exports a file whose script tag
  dangles, so the opened copy shows the static fallback text and never runs (the garden JSON is still inside
  it, so the data is recoverable, but not usable). The test harness would still pass. Any extraction must
  inline local assets in `exportPortable` first and add a test that opens the export from `file://`.
- **F77 (low, the recommended path).** A classic-script split into a few files is behaviour-neutral
  (measured byte-identical rendering); ES modules break the `file://` portable copy and a bundler conflicts
  with the no-root-`package.json` rule. Order: CI and characterization tests (F30, F31), one format-only
  prettier commit with relaxed test regexes (F21, F45), reference data to its own classic script (F75),
  CSS out, then JS in three or four files with the service-worker changes from F29.
- **F22, F74, F73, F76 (low–medium).** A pure core (~8 % of the script) could run under node without a
  browser; state is a reassigned top-level `let`; dispatch is split across two click listeners with no
  drift check; `plans` means plantings and the stored key cannot be renamed without a migration.

### Horticultural data integrity (F23, F37, F38, F41, F48, F78–F84)

The no-fabrication rule holds in the data: every flower and every herb without a regional source has
`source: null` or empty windows, and the UI labels them. What could not be done here is checking the
numbers.

- **F37 (medium).** None of the 44 Lower Rio Grande Valley rows could be compared with the cited PDF
  (hosts blocked). The "checked October 1, 2026" note is the date of every commit, and 13 crops were added
  in one commit without changing it. This is an owner task: read the 2020 guide row by row and record a
  per-crop `verifiedOn`.
- **F41 (medium, unverified lead).** A search summary of the 2012, 2018 and 2022 editions shows
  different windows for beets, melon, corn and cucumber. The refutation pass could not open the 2020 PDF
  either and corrected the first reading: the differences are not a simple merge of spring and fall rows.
  The items to check first are the corn fall window (08-01 to 09-01, which other editions do not list) and
  the beet window (the app's November to January range falls outside the older guides). Do not change data
  on this basis; read the 2020 PDF row by row for beet, corn, melon, cucumber, squash, pumpkin and
  watermelon.
- **F38 (medium).** Herb detail dialogs say "this flower" and label an app default as "Guide's starting
  method". Copy fix.
- **F23 (medium).** Nine windowless herbs never appear in the default Month view; searching "basil" says
  nothing matches.
- **F78–F84 (low).** Basil's 60–90 days has no attributable source; the 40 % compost flag cites guidance
  that was not confirmed; zone 10a is asserted rather than confirmed; the cauliflower correction is
  hard-coded in UI text; five single-value harvest figures and a bok choy/napa duplicate look like
  transcription candidates; flowers show a placeholder as their family.

### Security and privacy (F05, F18, F27, F63)

- No third-party scripts, analytics, fonts or keys. All four external links use `rel="noopener
  noreferrer"`. The portable export neutralises `</script` and `<!--`. Photos lose EXIF, including GPS.
- **F27 (medium).** No security headers. The app is a clean CSP candidate (no inline handlers, no `eval`,
  one inline script): a hash-based `script-src` was shown to work and would have blocked F05. Recommended
  `vercel.json` headers are in Appendix A under F27; the hash must be regenerated by a `tools/` script on
  every change.
- **F63 (low).** Backups and the portable copy are plain text with a short warning; add the warning at
  save time, "private" to the filename, and consider encrypted backups before cloud sync.
- The security checklist for the future sync and AI work is in `docs/SYNC-ARCHITECTURE.md`.

## What is done well

Escaping discipline (`h()` on every user string but the four in F05); `validateState` as a real gate
on load and import; conservative delete cascades; share-sheet-first export with download and copy
fallbacks; a minimal service worker that never caches personal data; correct date math across DST and
New Year; correct unit constants and gram-per-10-gallon conversion; native `<dialog>` with focus trap
and Escape; 16 px inputs, safe-area handling, 44 px primary targets, reduced-motion support, pinch zoom
left enabled; honest estimate language and an explicit source notebook; the cauliflower date correction
disclosed rather than silent.

## Appendix B: how the evidence was produced

Every runtime finding came from a Playwright script run against the served `index.html` in Chromium
(phone emulation at 320 px and 390 px unless stated). The scripts live in the audit session's scratch
directory, not in the repository; the repeatable parts were turned into `tools/tests`. Severity and
bucket assignments were made by the coordinating session after reading each finding; the refutation pass
(column "Verification") was an independent agent told to refute the finding, which read the pre-fix code
and the current branch and re-ran the measurement where possible.
